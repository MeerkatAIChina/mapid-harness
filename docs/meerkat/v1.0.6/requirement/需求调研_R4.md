### 1.2 依赖与环境

- pip：requests、matplotlib+numpy、python-docx、reportlab、Pillow、websocket-client（仅 Chrome 公式渲染用）——全是常见包；
- 外部二进制：**Chrome 是主要摩擦点**（探测全是 Linux 名，Windows 需设 `LONG_REPORT_CHROME` 或补 5 行探测）；pdfinfo 是软依赖（缺失仅少页数统计）；
- 字体：Windows 直接落到雅黑/宋体**无需改代码**；DGX 需 vendor Noto 字体目录（`LONG_REPORT_FONT_DIR` 指向）；注意雅黑与 Noto 行高差异会让 PDF 排版与原作者产物不同；
- 公式渲染建议换 **matplotlib mathtext**（零新增依赖、跨平台，改造约 80~120 行 / 0.5~1 人日），保留 `LONG_REPORT_MATH_BACKEND=chrome` 回退；风险：mathtext 对公式内中文支持差，需预处理。

### 1.3 接缝契约（喂我们的 md 怎么接）

最干净接入点 = `report_renderer.convert(fmt, md_text, output_path)`：单文件 md 字符串进，三格式出。
图表走 ` ```chart ` fenced JSON（schema 13 类型，validate() 入库前校验）；公式走 `$..$`/`$$..$$`。
**风险：其自研极简 md 解析器对不认识的语法（脚注、多层嵌套列表、HTML 块）会静默吞成普通段落——
必须用我们的真实语料先跑一次解析保真度实测**（round-4 产物即现成测试集）。

### 2.2 审校链（B1）：接入点现成

- merge 闸已在 `_pre_tool_call` 拦 `merge_chapters`（chapter_gate.py:206-238），加「存在未过审校的章 → 阻断」
  是完全现成的模式；状态机加一个 `reviewed` 维度即可；
- **独立模型调用通路存在且合适**：`PluginContext.get_model_access(spec)` → `ModelAccess.invoke_text`
  （支持 system/temperature/timeout_s/`response_format="json"`），不进主 agent 对话流——审校模型
  走这条路，天然满足「角色分离」；
- **坑 4 个**：①门禁状态全在内存，重启即丢（与 A4 放行落盘合并解决）；②merge 闸只拦 merge_chapters
  工具，直接编辑 report_merged.md 不感知；③改章置待评后不会自动复测（merge 闸现场重算兜底）；
  ④审校引入的新脏消耗既有拦截额度（repair_rounds 语义要在设计阶段定清）。

### 2.3 看门狗（A5）：最小改动点确认

挂起不抛异常 → 现有 retry 层全部抓不到（实证判断正确）。最小改动 = 新增 `wrap_model_call` 中间件，
`asyncio.wait_for` 包住调用、超时抛可重试异常；**位置必须在 patient_retry 内侧**（每次重试独立计时），
挂载照抄 chapter_gate 的 env/config flag 模式。无内核改动。

### 2.4 回源核验（A1）：searchfree 能撑半段

- searchfree 返回 `{title, url, snippet}` JSON，结构化可程序解析 ✅；**但 snippet 无正文**，
  目标数值未必落在摘要里 ❌；
- 结论：「检索半段」可用，需配套**正文抓取工具**（web_fetch 或新工具）+ 模型做断言-证据比对；
  硬事实零容忍场景需多查询冗余 + 官方源优先策略（无域名权威度过滤是 searchfree 现状）。

### 2.5 台账增速（B4）：检查器基本不用改

增速行金缺陷回归已在用（GD-09 靠 numeric_consistency 检出）。但三个点：
1. 指标名是精确字符串分组键——「营收同比增速」vs「营收 YoY」会碎成两组，**命名规范钉死在提示词层**；
2. **`numparse._SPAN_RE` 不含负号**：「-0.35%」与「+0.35%」解析同值误判兼容——增速成批入台账后
   这是真实漏检面，**建议纳入 R4 顺手修**（补录 §4）；
3. 口径聚类靠子串规则，增速口径写法需保持包含关系（提示词层钉）。

### 2.6 续写前台化（谨慎吸收项）：触点现成

最自然触点 = `chapter_gate._post_tool_call` 的 report_stats 分支——既有附言回路零新增触点：
「实测字数 vs outline 目标不足 → 附言给补写指引 + 章置 dirty」→ dirty 章自动被开新章拦截，
构成闭环。注意：现有 `check_word_count` 只查自报偏差（GD-13），**「目标字数」是新契约**，从 outline 读。

## 5. 阻塞项与风险

- **硬阻塞：无。**
- 软风险：①Chrome 依赖（有 mathtext 替代，降级路明确）；②searchfree 无正文抓取（需配套工具，
  工作量新增）；③审校模型选型——同家族模型可能背错同一知识（TRIZ 报告实证），设计阶段评估
  「审校模型 ≠ 生成模型」或「审校 + 检索证据」组合；④三格式渲染的中文字体跨平台一致性
  （vendor 字体解决，需拿 Noto 字体文件）。

## 6. 建议实施顺序（供设计/执行计划参考）

1. **引用格式先行**（C5 提示词 + 格式约定）→ 检查器三级判定 + GD-06 同批（顺序钉死）；
2. 看门狗（A5，独立小件，先解决挂起这个最大过程痛点）；
3. 残留清理 + 占位符检查器（B2/A2，确定性工具，最快见效）；
4. 渲染管线移植（C1/C2/C3 + R-5 保真实测先行）；
5. 图表工具（C4，挂台账契约 + R-3 语义统一）；
6. 审校链（B1，依赖 2.2 的通路验证）；
7. 回源核验（A1，最重，配套正文抓取工具）；
8. 续写前台化 + 放行落盘 + 附言改进（A4/A6/A7 + 谨慎吸收项，门禁一批做）。
