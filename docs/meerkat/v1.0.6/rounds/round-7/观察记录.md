## 三、机制级新发现（本轮核心产出，R5 立项候选）

### M1. 核验无去重、无缓存（成本主因）

- 同一断言被重复核验最多 **10 次**（ch2 实证：「佛山照明通过收购国星光电切入封装…」等 3 条各 10 次）。
- 根因链条：审校改文 → 该章 verified 作废（「编辑即清」设计）→ 全章重核；重核时重新抽取，
  措辞漂移产生「新断言」，旧判定无法复用；每章实际被全量核验 2~3 遍。
- 修复方向：按断言规范化哈希缓存判定结果（章内+跨章）；重核只核「受编辑影响」的断言子集
  （或至少先查缓存再调模型）。

### M2. 抽取上限失效 + 垃圾断言

- 修复 commit 2a728d2 定的「最多 20 条」未兜住：ch2 去重后仍有 180 条独立断言
  （多次抽取叠加，每次 ≤20 条但总量无封顶）。
- 抽到了 Markdown 表格行 / 版式碎片当断言（如「│ 第三层 竞品层：10家拆解 + 参数/渠道对标 │」），
  这类必然判 unverifiable/refuted，纯浪费调用且污染判定统计。
- 修复方向：章级断言总量封顶；抽取后过滤非陈述句（表格行、目录碎片、纯版式行）。

### M3. judge 判定准确率不合格（留待验证项的实证）

- **自相矛盾**：同一事实「2025 年中国 LED 下游应用市场规模 5056 亿元，同比 -0.4%」
  在 ch1 判 confirmed、ch2 判 refuted。
- **真陈述被证伪**：「雷士照明中国业务自 2019 年起由 KKR 控股的非上市主体运营」
  （与 progress.md 模型自记事实一致）被判 refuted。
- **重复证伪**：同一断言（木林森境外收入 95.86 亿元/54.97%）以措辞微差两次被判 refuted。
- unverifiable 占比 48%~70%（ ch1 61%、ch2 48%、ch3 70%）：按现行 merge 语义
  （查无实证必须降级+[待核实]，否则 merge 硬失败），13 章走完 merge 大概率被卡死
  或逼出满篇 [待核实] 标注。
- 修复方向：judge 换更强模型（OCTOP_VERIFY_MODEL 独立通路就是为此留的）；
  判定前先把断言与台账/前章判定对账（同源同判）；检索无结果与证据不足要分开归因。

  `_INTERNAL_LC_SOURCES` 过滤该来源，不再流进聊天界面。94 个相关测试绿。
- **④根因已查明，属 octop 侧传输层，不修（fork 随主仓升级，只记录）**：
  - 证据链：11-04 23:03:06 日志 `ws hub: push failed`，uvicorn 报
    `sent 1011 keepalive ping timeout`——聊天 WS 已被判死；23:04 用户点停止，
    前端 `sendCancelFrame` 仅在 `ws.readyState===OPEN` 时发送
    （`dashboard/src/pages/Chat/hooks/chatStore.ts:843`），socket 已死则 cancel 帧
    静默丢弃，服务端从未收到 → 模型继续生成，23:09 撞 31KB 截断落库（seq19）。
  - harness 取消链路排查后确认完好：`manager.cancel` → `agent.cancel(thread_id)` →
    `_iter_until_cancelled` 抢占取消挂起的 `__anext__`；patient_retry / empty_guard /
    model_watchdog 三中间件均不吞 CancelledError（`except Exception` 捕不到
    BaseException）；langgraph 层实测 cancel 后节点任务终止；thread_id 全链路同源
    （新会话先 createSession 拿服务端 tid 再 sendTurn）。
  - 修复方向（记录给 octop 主仓/后续决策）：加 HTTP 取消端点
    `POST /agents/{id}/chat/cancel`，前端 socket 非 OPEN 时走 HTTP 兜底；
    顺带评估 uvicorn ws keepalive 参数（长生成期间事件循环繁忙可能挤占 pong）。
  - 与③同源：同一条易死连接——③是显示层症状（重放旧缓存），④是控制通道症状。
- **②连接泄漏：定性为上游 httpx keep-alive 设计行为，无功能损害，不修**：
  - 机制：模型服务端挂断后，本地 socket 滞留在 httpx 连接池（CloseWait）。
    httpx 的 `keepalive_expiry`（默认 5s）只在**下次取用连接时**清扫，池子
    完全空闲期间不主动回收。round-6 的 94 分钟僵尸正好横跨 21:48 停摆到
    23:02 新会话——期间零模型流量；恢复活动后该连接会被正常清扫，复用时
    httpcore 也会识别已关闭连接并丢弃重建，不会把死连接发给新请求。
  - harness 的 ChatModelFactory 不自建 httpx client（langchain-openai/openai
    SDK 默认池），没有自增的泄漏面。若未来在意 fd 占用，可加周期池清扫，
    现阶段不建议为此加机制。
- **③ws 重放旧缓存：主因已由⑤消除，残余为 octop 前端 UX，不修**：
  - ws_hub 无任何缓存/重放缓冲（`infra/gateway/ws/ws_hub.py` 全文确认），
    重连只补**未来** chunk（`test_ws_rebind_after_disconnect_receives_later_chunks`
    明确此语义）。
  - 「重放旧缓存」观感 = 刷新后从 DB 历史投影重载（落后于进行中 turn）+
    当时⑤把核验输出刷进聊天界面 + 机制层病态重复内容，三者叠加。⑤修复后
    主因消除；断连重补的 UX gap 留给 octop 主仓。
- **①循环停摆：证据定界到「graph 内部工具节点结束→下一模型节点未进入」，
  无法事后定到具体行，补强观测**：
