## 五、基建事故记录（deepagents gbk bug）

- **根因**：`deepagents/backends/filesystem.py:1004` `_ripgrep_search` 以系统默认编码（Windows GBK）读 ripgrep 输出，遇 UTF-8 中文报告文件崩溃；turn 以 `kind=stream` 失败。**第三方库 bug，Octop/mapid-harness 零代码责任**。
- **触发条件**：v4 工序 a~e 让模型首次使用 grep/read_file/edit_file 自查（round-2 无 grep 调用所以未触发）。
- **时间线**：10:36 首崩（grep）→ 10:45 用户点重试恢复；11:24 二崩（grep）→ 后端带 `PYTHONUTF8=1` 重启 → 前端「重试」按钮失效（`handleRegenerate` 链路静默无动作，原因未完全定位，active-model 空记录为嫌疑但非确证）→ 13:44 改发「继续」恢复。
- **干预会计**：2 次人工动作（重试点击、「继续」消息）+ 1 次后端重启。性质为基建 bug 恢复，非生成行为问题；但按既定口径，过程指标 0 干预记 ❌。
- **衍生发现（前端健壮性，非本轮范围）**：后端重启后前端「重试」按钮失效且无报错提示；「重试」= 原样重发整段任务书（10:45 已发生一次），对长任务有「模型重启任务」风险，手动「继续」是更优恢复路径。
- **附带噪音**：11:27 用户聊天 thread（thr_01M5E63…S7）记忆提取 light 档调用失败一次（degraded），与本轮无关。
