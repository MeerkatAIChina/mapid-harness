# 基于 Octop Harness 二次开发的消费品咨询行业深度分析的 Harness

本目录归档 Meerkat（基于 Octop 私有 fork 的二次开发）的**所有版本的全部需求/调研/设计/计划文档**，目标是每个二开需求都可追溯：**需求 → 调研 → 设计 → 决策 → 计划 → 实现**，任何一环都能指回上一环。

## 目录结构

```text
docs/meerkat/
  README.md             ← 本文件：目录说明与归档约定
  v1.0.n/               ← 一次迭代 = 一个版本目录
    requirement/        ← 业务方原始需求（产品定位、客户、功能、约束）
    research/           ← 针对需求的代码库调研结论（可行性、机制、边界）
    specs/              ← 定稿设计文档（评审通过，开发依据）
    plans/              ← 任务级实施计划（Task 拆解 + checkbox 追踪，执行依据）
    ADR.md              ← 架构决策记录（关键取舍 + 被否决方案及原因）
    CHANGELOG.md        ← 相对上一版本的变更记录（Added/Changed/Fixed/Known Issues）
```

## 归档约定

1. **一次迭代，一个版本目录**。按 `v1.0.0`、`v1.0.1`、`v1.0.2` 递增（低位跟随 Octop 上游版本号，不用 1.x）；目录一旦随对应开发完成而冻结，不再修改。需求变更或返工走新版本目录，不回改旧目录。
2. **五件套齐全才算归档完成**（交付型需求另加交付三件套）：
   - `requirement/` —— 业务语言写就，回答「做什么、为谁做、为什么」；
   - `research/`    —— 对着代码库写，回答「现状是什么、哪些能复用、边界在哪」，每个结论须指明文件与位置；
   - `specs/`       —— 设计定稿，回答「怎么实现」，须经评审通过（评审中发现的必修项全部闭环）后方可作为开发依据；
   - `plans/`       —— 把设计文档拆成可执行的 Task 序列，回答「按什么顺序、用什么步骤实现」，每个 Task 含文件清单、接口契约、测试与提交步骤，checkbox 逐项追踪进度；须经评审通过后方可动工，执行中的完成状态实时回写本文件。
   - `ADR.md`       —— 只记「关键取舍」，每条含背景、决策、被否决方案及原因、后果；
   - `CHANGELOG.md` —— 相对上一版本的全部变更（Added/Changed/Fixed/Known Issues），core 内核缝改动单独标注并指回 ADR。
3. **与 Octop Harness 自身文档的边界**。`docs/meerkat/` 之外的文档属于 Octop Harness，保持与上游字节一致；Meerkat 的所有文档只写在本目录下，保证 `update-qm` 合并上游时零冲突。
4. **分支约定**：
   1. `main` 只用于跟随上游主仓升级，保持与 upstream 可快进合并的状态，**二开成果一律不合并回 `main`**；
   2. **`meerkat` 分支作为我们自己的生产环境发布分支**，不允许在这个分支进行开发、提交代码等操作。
   3. 所有二开开发在功能分支（如 `feature/meerkat-dev`）上进行，上游同步由 `update-qm` 向功能分支合并 upstream/main；

5. **设计文档与实现的一致性**。实现过程中对设计的偏离，必须回写 `设计文档.md`（冻结前）或在 `ADR.md` 补一条新决策（冻结后），不允许代码与文档长期分岔；执行计划与实际顺序的偏离同理，回写 `执行计划.md`。
