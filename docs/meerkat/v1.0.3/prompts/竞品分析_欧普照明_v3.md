# 任务提示词 v3：欧普照明竞品分析深度报告

> 版本：v1.0.3 · 2026-10-19
> v2 → v3 变更（对应设计 §3.1/§2.2 与评审意见）：
> 1. 新增**软门禁自检清单**（每章写完自问三条，只引导不拦截）
> 2. `data_ledger.md` 改为**结构化表格 schema**（指标名|数值|单位|口径|来源|首现章节）
> 3. 新增**「财务数据先搜后写」**（时效性红线）
> 4. 字数口径写明（非空白字符数）+ **禁止自报字数**，必须用 `report_stats` 工具
> 5. **禁止自写脚本合并**，必须用 `merge_chapters` 工具
> 6. 运行时当前日期会由系统注入，所有落款/台账日期以注入日期为准

---

```text
任务：欧普照明竞品分析深度报告

核心工作方式（最高优先级，先于一切内容要求）
本任务是一份 10 万字量级的长报告，单次回复不可能装下全文，这是工程事实而非偷懒借口。你必须采用「分章写文件」的工作方式，通过文件系统工具在工作目录中逐章产出，最终用内建工具合并为完整报告。具体要求：

1. 先规划后写作：第一步必须先写出大纲文件 outline.md（章节目录 + 每节要点 + 每章预估字数 + 各章数据来源计划），然后再开始动笔。
2. 逐章产出：每个一级章节写入独立的 Markdown 文件（chapters/01_研究背景.md、chapters/02_行业全景.md ……依此类推）。每次 write_file 调用只写一节内容（单节控制在 2000–4000 字），一章分多次调用写完，严禁试图在一次回复中输出整章甚至全文。
3. 维护进度台账：持续更新 progress.md，记录已完成章节、待办章节、写作中发现的问题。每完成一章就更新一次。注意：progress.md 中禁止自报字数，字数统计一律使用 report_stats 工具的结果。
4. 维护数据台账（结构化）：持续更新 data_ledger.md，格式必须是如下表格，禁止自由文本：

   | 指标名 | 数值 | 单位 | 口径/年份 | 来源 | 首现章节 |
   |---|---|---|---|---|---|
   | 欧普照明营业收入 | 70.96 | 亿元 | 2024年报 | 欧普照明2024年年度报告 | 03 |

   报告中出现的所有关键数值（市场规模、财务数据、份额、技术参数）都必须登记。后续章节引用同一数据时，必须先查台账，保证全文数值、单位、口径完全一致。
5. 章节自检清单（每章写完、开始下一章之前，逐条自问并落实）：
   - 台账更新了吗？本章出现的关键数值都已登记进 data_ledger.md？
   - 本章数值与台账中已有条目一致吗（同指标同数值同口径）？
   - 本章无法查证的数据都标注了「[待核实]」吗？
6. 合并交付：全部章节完成后，必须调用 merge_chapters 工具合并为完整报告，严禁自己编写脚本或手动拼接合并。合并后用 report_stats 统计字数，把工具输出原样写入 progress.md。

一、任务主题
撰写一份欧普照明（Opple Lighting）竞品分析深度研究报告，全文字数目标 10 万字（中文，以非空白字符数计）。

二、篇幅与结构要求
- 全文展开为多章节、多层级的完整报告（建议 12–15 个一级章节，每章下设 3–6 节），严禁只输出大纲充数。
- 每个一级章节正文 6000–12000 字，总字数逼近 10 万字。
- 内容不足以达字数时，围绕以下方向加深加厚，而不是注水：
  - 欧普照明 vs 雷士照明、佛山照明、三雄极光、阳光照明、公牛集团、木林森、飞利浦（昕诺飞）、欧司朗（艾迈斯欧司朗）、松下照明、Yeelight/小米生态链等竞品的逐家深度拆解；
  - 各竞品的产品线矩阵、价格带分布、渠道结构（线下经销/五金渠道/电商/工程集采/海外）逐一对比；
  - 智能照明赛道（Matter 协议、全屋智能、人因照明 HCL）的技术路线对比；
  - 财务指标多年度纵向对比（营收、毛利率、净利率、研发投入占比、存货周转等）。

三、建议章节框架（可扩展）
1. 研究背景、方法与数据来源说明
2. 中国及全球照明行业全景：市场规模、增速、产业结构、政策与标准（能效标准、双碳政策影响）
3. 欧普照明公司深度剖析：发展历程、股权与治理、业务结构、财务分析、战略路线
4. 竞争格局总览：市场份额、梯队划分、竞争五力分析
5. 重点竞品逐家深度分析（每家独立成节：公司概况、产品、渠道、财务、优劣势）
6. 产品线与技术参数横向对比：光源效率、显色指数、色温范围、智能协议支持、质保等
7. 渠道与营销对比：渠道结构、终端网点数量、电商表现、品牌投放
8. 智能照明与新技术布局对比：专利分析、协议生态、全屋智能合作
9. 财务与经营指标综合对标（多年度）
10. SWOT 与战略群组分析
11. 行业趋势研判与欧普照明的机会/威胁
12. 结论与战略建议
13. 附录：数据来源清单、术语表、待核实数据清单

四、图文并茂要求
- 使用 Mermaid 图表、Markdown 表格、文本示意图呈现市场份额、财务趋势、对比矩阵等；
- 每张图/表必须配文字说明与数据解读（图题 + 来源标注 + 至少一段解读），不允许无解读的孤立图表。

五、数据真实性硬性要求（红线，优先级高于篇幅）
- 时效性：涉及公司财务数据时，必须先搜索确认该公司最新一期已披露的财报（年报/季报），引用最新数据，禁止使用过期的旧数据而不自知；行业数据优先采用最近年份的权威发布。
- 所有技术参数、市场规模、专利数据、竞品数据、财务数据、行业标准必须来自真实可查证来源（年报/招股书、国家统计机构、行业白皮书、券商研报、官方标准、专利数据库），引用处标注来源（精确到报告名+年份）。
- 严禁虚构数据，严禁用"看起来合理"的经验数字填充。无法确认的数据必须标注「[待核实]」并说明建议核实渠道。
- 所有「[待核实]」数据在附录汇总为《待核实数据清单》表：数据项、所在章节、建议核实来源。
- 同一数据在全文多处出现时，数值、单位、口径必须与 data_ledger.md 台账完全一致，禁止前后矛盾。
- 结论章的每条论断必须能在前文找到对应论据；评价标准（比较对象、指标）在全文中保持一致，如需更换比较口径必须显式说明理由。

六、语言与交付
- 全文简体中文；术语首次出现附英文原词。
- 交付物：outline.md、data_ledger.md（结构化表格）、progress.md、chapters/ 目录下全部章节文件、经 merge_chapters 工具合并的完整报告。
```

## v2 → v3 变更对照

| 项 | v2 | v3 | 对应机制 |
|---|---|---|---|
| 台账格式 | 自由 Markdown | 结构化表格（6 列固定 schema） | D2/D4 数值比对可靠性（设计 §2.2） |
| 字数统计 | 模型自报 | 禁止自报，必须用 `report_stats` | D2（基线缺陷 #1/#2） |
| 合并方式 | 模型自写脚本 | 必须用 `merge_chapters` | 基线缺陷 #6 |
| 章节自检 | 无 | 每章三问清单（软门禁） | 设计 §3.1 |
| 时效性 | 未提 | 财务数据先搜后写 | D1 新增（评审意见 #5） |
| 结论约束 | 未提 | 判据一致、换口径须声明 | D3 判据置换（设计 §2.3） |
| 日期 | 未提 | 以系统注入日期为准 | T5 日期注入 |
