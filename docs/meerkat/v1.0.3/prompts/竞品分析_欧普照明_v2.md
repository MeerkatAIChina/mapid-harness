# 任务提示词 v2：欧普照明竞品分析深度报告

> 版本：v1.0.3 · 2026-10-16
> 变更说明：基于 v1（用户原版）改造。**核心反转：v1 强制「单次输出全文」导致撞 81920 token 服务端 cap（根因，见调研文档第 8 节）；v2 改为「分章写文件」工作流**，其余结构/红线/图表要求基本保留。
> 用法：基线测试时建议先把字数目标改为 2~3 万字（见文末「基线缩放」），验证工作链后再放 10 万字全量。

---

```text
任务：欧普照明竞品分析深度报告

核心工作方式（最高优先级，先于一切内容要求）
本任务是一份 10 万字量级的长报告，单次回复不可能装下全文，这是工程事实而非偷懒借口。你必须采用「分章写文件」的工作方式，通过文件系统工具在工作目录中逐章产出，最终合并为完整报告。具体要求：

1. 先规划后写作：第一步必须先写出大纲文件 outline.md（章节目录 + 每节要点 + 每章预估字数 + 各章数据来源计划），然后再开始动笔。
2. 逐章产出：每个一级章节写入独立的 Markdown 文件（chapters/01_研究背景.md、chapters/02_行业全景.md ……依此类推）。每次 write_file 调用只写一节内容（单节控制在 2000–4000 字），一章分多次调用写完，严禁试图在一次回复中输出整章甚至全文。
3. 维护进度台账：持续更新 progress.md，记录已完成章节、字数统计、待办章节、写作中发现的问题。每完成一章就更新一次。
4. 维护数据台账：持续更新 data_ledger.md，登记报告中出现的所有关键数值（市场规模、财务数据、份额、技术参数）及其来源、数值口径、首次出现章节。后续章节引用同一数据时，必须先查台账，保证全文数值完全一致。
5. 合并交付：全部章节完成后，按大纲顺序合并为完整的 report.md（含目录），并统计全文字数写入 progress.md。

一、任务主题
撰写一份欧普照明（Opple Lighting）竞品分析深度研究报告，全文字数目标 10 万字（中文）。

二、篇幅与结构要求
- 全文展开为多章节、多层级的完整报告（建议 12–15 个一级章节，每章下设 3–6 节），严禁只输出大纲充数。
- 每个一级章节正文 6000–12000 字，总字数逼近 10 万字。
- 内容不足以达字数时，围绕以下方向加深加厚，而不是注水：
  - 欧普照明 vs 雷士照明、佛山照明、三雄极光、阳光照明、公牛集团、木林森、飞利浦（昕诺飞）、欧司朗（艾迈斯欧司朗）、松下照明、Yeelight/小米生态链等竞品的逐家深度拆解；
  - 各竞品的产品线矩阵、价格带分布、渠道结构（线下经销/五金渠道/电商/工程集采/海外）逐一对比；
  - 智能照明赛道（Matter 协议、全屋智能、人因照明 HCL）的技术路线对比；
  - 财务指标多年度纵向对比（营收、毛利率、净利率、研发投入占比、存货周转等）。

三、建议章节框架（可扩展）
1. 研究背景、方法与数据来源说明
2. 中国及全球照明行业全景：市场规模、增速、产业结构、政策与标准（能效标准、双碳政策影响）
3. 欧普照明公司深度剖析：发展历程、股权与治理、业务结构、财务分析、战略路线
4. 竞争格局总览：市场份额、梯队划分、竞争五力分析
5. 重点竞品逐家深度分析（每家独立成节：公司概况、产品、渠道、财务、优劣势）
6. 产品线与技术参数横向对比：光源效率、显色指数、色温范围、智能协议支持、质保等
7. 渠道与营销对比：渠道结构、终端网点数量、电商表现、品牌投放
8. 智能照明与新技术布局对比：专利分析、协议生态、全屋智能合作
9. 财务与经营指标综合对标（多年度）
10. SWOT 与战略群组分析
11. 行业趋势研判与欧普照明的机会/威胁
12. 结论与战略建议
13. 附录：数据来源清单、术语表、待核实数据清单

四、图文并茂要求
- 使用 Mermaid 图表、Markdown 表格、文本示意图呈现市场份额、财务趋势、对比矩阵等；
- 每张图/表必须配文字说明与数据解读（图题 + 来源标注 + 至少一段解读），不允许无解读的孤立图表。

五、数据真实性硬性要求（红线，优先级高于篇幅）
- 所有技术参数、市场规模、专利数据、竞品数据、财务数据、行业标准必须来自真实可查证来源（年报/招股书、国家统计机构、行业白皮书、券商研报、官方标准、专利数据库），引用处标注来源。
- 严禁虚构数据，严禁用"看起来合理"的经验数字填充。无法确认的数据必须标注「[待核实]」并说明建议核实渠道。
- 所有「[待核实]」数据在附录汇总为《待核实数据清单》表：数据项、所在章节、建议核实来源。
- 同一数据在全文多处出现时，数值与口径必须与 data_ledger.md 台账完全一致，禁止前后矛盾。

六、语言与交付
- 全文简体中文；术语首次出现附英文原词。
- 交付物：outline.md、data_ledger.md、progress.md、chapters/ 目录下全部章节文件、合并后的 report.md。
```

## v1 → v2 变更对照

| 项 | v1 | v2 | 理由 |
|---|---|---|---|
| 输出方式 | 强制单次输出全文 | 分章写文件 + 合并 | v1 指令直接撞 81920 token cap（根因） |
| 大纲 | 无要求 | 先写 outline.md | 让模型显式规划，防止写着写着丢结构 |
| 数据一致性 | 仅泛要求 | 强制 data_ledger.md 台账，引用先查台账 | 针对「数值漂移」「跨章矛盾」两类致命缺陷 |
| 进度管理 | 无 | progress.md | 长任务中断可续；也便于我们观察工作链 |
| 单节长度 | 未约束 | 单节 2000–4000 字/次调用 | 单次 write_file 远低于 cap，杜绝截断 |
| PDF 交付 | 要求 PDF | 暂缓（先 Markdown） | agent `main` 禁用了 nano-pdf skill，PDF 链路后续单独解决 |
| 结构/红线/图表 | 原文 | 保留 | 原版写得很专业，无需改动 |
