# 需求调研：十万字报告产出能力

> 版本：v1.0.3 · 调研日期：2026-10-16 · 调研人：Claude（逐轮驱动，本文档为第 1 轮产出）
> 关联需求：`harness 调优.md`（桌面）—— 基于 Octop Harness 二次开发，面向消费品咨询行业深度分析报告的 Harness 调优
> 本文档聚焦 TODO 第 ① 项「让 Agent 能产出 10 万字」的前置调研，同时覆盖第 ③ 项（可观测性）现状。

---

## 0. TL;DR（结论速览）

1. **「单次输出上限」不是 Harness 的硬限制，也不是模型的宿命。** Harness（OpenAI 兼容协议下）发起请求时**不带 max_tokens**，实际 cap 落到了 vLLM 服务端默认的 `max_new_tokens=81920`。而且报告本来就不该单次生成——Harness 的设计是模型通过 `write_file`/`edit_file` 工具**多次写文件拼出长文**。上次任务只写 5 万字并称「受单次输出上限限制」，最可能是**模型自我认知 + 提示词缺失**（没人告诉它应该分章写文件），属于行为问题而非能力问题。
2. **Harness 没有任何「报告生成」专用机制**：没有大纲→分章管线、没有续写保证、没有 report skill。长文产出完全依赖模型自主决策——这正是调优的主战场。
3. **可观测性现成可用**：Octop 侧有 Trajectory 系统（每轮 user/assistant/tool/context 事件落库 `trajectory_events` 表，dashboard 有轨迹面板）；Harness 侧有 Langfuse 集成（LLM 请求级 trace）+ checkpointer 消息历史。第 ③ 步大概率是「接入+补全」而非自建。
4. **模型侧事实**：TRIZ 部署为 vLLM LoRA（基座 Qwen3.6-35B-A3B NVFP4），上下文 256K，服务端默认输出 cap 81920 token，`temperature=0`，**思考模式被强制关闭**（`enable_thinking: false`）。
5. **借鉴蓝本已找到**：deepcode-cli 的「能力注册表 + 缓存感知布局 + 容错工具契约 + Skills 按需加载 + 实证驱动提示词」与我们的调优需求高度同构。

## 1. 模型服务侧调研（192.168.60.102）

### 1.1 TRIZ 模型（端口 8000）

部署方式：Docker 容器 `meerkat-triz-vllm-nvfp4-v2`，镜像 `vllm/vllm-openai:v0.25.0`，GPU NVIDIA GB10。

关键启动参数（`vllm serve`，2026-10-14 启动）：

| 参数 | 值 | 含义/影响 |
| --- | --- | --- |
| 基座模型 | `/models/base` = `Qwen3.6-35B-A3B-NVFP4-Fast` | NVFP4 量化，MoE（A3B=激活 3B） |
| LoRA | `Meerkat-TRIZ-v1=/models/adapter`，`--max-lora-rank 64` | TRIZ 领域适配器，`/v1/models` 可见 |
| `--max-model-len` | **262144**（256K） | 上下文窗口足够大，不是瓶颈 |
| `--override-generation-config` | `{"temperature": 0.0, "repetition_penalty": 1.0, "max_new_tokens": 81920}` | **服务端默认单次输出上限 81920 token**；温度为 0（确定性输出） |
| `--default-chat-template-kwargs` | `{"enable_thinking": false}` | **思考模式默认关闭** |
| `--max-num-batched-tokens` | 8192 | 吞吐相关 |
| `--max-num-seqs` | 64 | 并发 64 |
| `--reasoning-parser` | qwen3 | 支持 reasoning 解析（但 thinking 默认关） |
| 工具调用 | `--enable-auto-tool-choice --tool-call-parser qwen3_coder` | OpenAI 兼容工具调用可用 |
| `--enable-prefix-caching` | 开 | 稳定前缀可吃缓存，多轮报告任务受益 |
| 多模态 | image ≤10 张 1280px / video 1 段 | 支持图文输入 |

API 验证：`GET /v1/models` 返回 `Qwen3.6-35B-A3B-NVFP4-Fast`（max_model_len 262144）与 `Meerkat-TRIZ-v1`（LoRA）。

**关键推算**：81920 token 对中文约 5~8 万字（Qwen 分词器 1 汉字 ≈ 1~1.5 token）。即**即使单次调用跑满服务端默认 cap，也只够 5~8 万字**——与上次任务「写了 5 万字就停」的现象吻合。10 万字必须靠多次调用（分章写文件）拼接，或者调大服务端 cap。

### 1.2 Laya 模型（端口 9000）

- 容器 `laya-laya-serve-1`（镜像 `laya-laya-serve`），**不是 OpenAI 兼容接口**。
- API（来自 `/openapi.json`）：
  - `POST /v1/systemone` — 单次结构化裁决
  - `POST /v1/systemone/batch` — 批量
  - `GET /health`
- 协议（容器内 `/opt/laya/examples/request.json`）：

```json
{
  "state": { "body": "待裁决文本" },
  "questions": {
    "维度名": {
      "type": "choice | score | noul",
      "instructions": "问题描述",
      "criteria": { "选项A": "说明", "选项B": "说明" }  // choice 时为 dict，score 时为分级数组
    }
  }
}
```

- 三种问题类型：`choice`（分类）、`score`（分级打分）、`noul`（是非/有无判断）。
- **对评审机制的意义**：Laya 是 System-1 结构化裁决模型，天然适合做多维度评审打分（如「事实是否有来源支撑: noul」「数值一致性: score」），但不能做开放式长文评点。评审流程设计应是「Laya 出结构化裁决 → 我（Claude）做开放式分析」。

要点：

### 2.3 输出限制（Octop 侧）

- Provider 配置（base_url、模型清单、api_key）存 `~/.octop/octop.db` 的 `providers` 表（key 明文）；激活模型存 settings 表。**当前 TRIZ 的接入参数可以直接查这个库确认**（后续动作）。

### 2.4 日志与可观测性（Octop 侧）

- **Trajectory 系统**（重要）：`infra/history/trajectory/`，事件类型 `user/assistant/tool/context/compacted/system`，落库 `trajectory_events` 表；dashboard 有轨迹面板（`api/routers/chat/trajectory.py`）。每轮用户输入、assistant 输出（含 tool_call）、工具结果、system prompt、启用的 skills 都有记录。

## 3. Harness 侧调研（E:\projects\mapid-harness，分支 feature/triz）

### 3.1 编排方式

- `src/octop_harness/agent.py`：HarnessAgent 是 `deepagents.create_deep_agent` 的门面（依赖 `deepagents>=0.7.16,<0.8`，LangGraph 标准 agent loop：模型 ↔ 工具循环），外堆一长串 middleware（bootstrap → router → model_settings → …）。
- `multi_agent_demo/` 只是 `examples/11_multi_agent.py` 的运行产物（演示多 agent 注册/路由），**与长文生成无关**。

### 3.2 长文生成链路（核心发现）

**Harness 没有任何报告/长文档专用机制**：

- 全仓 grep `report/outline/chapter/章节/大纲` 无业务命中；内置 skills（`builtin/skills/en/`：plan、powerpoint、ocr-and-documents 等）无 report 类。
- 长文实际产出方式：agent loop 里模型自主多次调用 deepagents 的文件工具（`write_file`/`edit_file`/`append_file`）在 workspace 逐段写文件拼接。证据：`agent.py:1688-1696` 系统提示教模型用文件工具；`middleware/bootstrap.py:29` `_WRITE_TOOLS`。
- **是否分章完全由模型自己决定**，Harness 不提供分段保证或续写机制。若模型选择一次 `write_file` 写全文，就退化为单次 LLM 输出，直接撞 81920 cap。

### 3.3 输出上限（Harness 侧，逐层排查）

| 层 | 位置 | 行为 |
| --- | --- | --- |
| ModelConfig | `config/__init__.py:366` | `max_output_tokens: int = 0`，注释明确「仅元数据，除非 host 显式配置」 |
| provider 预设 | `providers/provider_template.json` | 内置预设（131072/65536/32768 等），不进请求 |
| profile 注入 | `llm/factory.py:827-849` | 写进 `model.profile`，**不 bind 到请求** |
| 主模型构建 | `llm/factory.py:282` `_build_openai()` | **不传 max_tokens** → OpenAI 协议请求不带该字段 → **吃服务端默认（81920）** |
| 每轮注入 | `middleware/model_settings.py:25-32` | 唯一注入点：host 经 `configurable["model_settings"]["max_tokens"]` 下发（Octop 的 agent config 配了才生效） |
| 辅助调用 | `memory/llm_client.py`、`llm/invoke_helpers.py` | 记忆子系统显式传，与主链无关 |
| `DEFAULT_MAX_TOKENS=128_000` | `context_usage.py:29` | 是输入上下文窗口估算，**不是输出上限** |

**结论**：Harness 层刻意不做输出上限兜底。对 TRIZ（OpenAI 兼容协议）而言，单次响应上限 = vLLM 的 81920 token，除非 Octop 侧 agent config 显式配了 `max_tokens`（待查库确认）。

### 3.4 可观测性（Harness 侧）

| 机制 | 位置 | 粒度 |
| --- | --- | --- |
| **Langfuse** | `observability/langfuse.py`（`langfuse.langchain.CallbackHandler`，per-request 注入 user/session/agent 元数据；`agent.py:1262` 绑到编译图） | **LLM 请求级**：每轮 prompt/response/工具调用完整 trace。可选依赖 `observability` extra |
| 文件日志 | `observability/logging.py`，`~/.octop-harness/logs/YYYY-MM-DD.log`（Octop 下用 `~/.octop/logs`），10MB×5 轮转，带 `[agent=<id>]` 标 | 诊断级 |
| Checkpointer | `agent.py:1788-1816`：默认 `AsyncSqliteSaver`（`{workspace}/{system_files}/checkpoints.sqlite`）；启用 octop-memory 则复用 Memory。**Postgres checkpointer 未启用**（`backends/postgres.py` 是 workspace 文件存储，不是 checkpoint） | 全量消息历史，`aget_history()` 可还原完整对话+工具链 |

## 4. 借鉴调研：deepcode-cli 如何针对单模型调优

来源：[lessweb/deepcode-cli](https://github.com/lessweb/deepcode-cli)（TypeScript，专为 deepseek-v4 调优的编码 agent）。设计哲学引自 Armin Ronacher《Better Models: Worse Tools》：**工具 schema 不是中立的，harness 应只为一个模型量身调优**。

### 4.1 具体手法（有一手源码佐证）

1. **系统提示极简 + 工具文档外置 + 按模型能力条件渲染**：基础提示一句话，内容全在 `templates/tools/*.md`；EJS 模板按模型能力（如是否多模态）注入不同文本，**工具集本身随模型能力切换**。
2. **推理强度控制走 API 参数不走提示词**：`reasoning_effort` 顶层参数；思考模式重放历史必须携带 `reasoning_content` 字段（提供商侧约束的专门适配）。
3. **缓存感知消息布局**：稳定前缀（系统提示/工具文档/AGENTS.md）全部放在易变内容之前吃 KV cache（实测命中率 99.5%，成本差 120 倍）；auto-compact 阈值 = 上下文窗口一半，compact 用专门的结构化总结 prompt。
4. **容错式工具契约（snippet 系统）**：`read` 返回带版本的 `snippet_id`，`edit` 必填——强制先读后改；非唯一匹配返回候选而非猜测；`replace_all` 要求声明 `expected_occurrences` 护栏；转义错误时用一次小 LLM 请求自修复重试。
5. **Skills 按需加载**：catalog（仅名称+描述）进上下文，模型自匹配，命中才加载全文——「技能不是插件，而是被结构化的上下文」。
6. **Plan Mode 实证**：三阶段模板使推理 token 占比 31.9%→48.7%，任务通过率 0%→75%，成本仅 +26%（有对照实验文档）。
7. **权限系统**：工具要求模型自我声明副作用（sideEffects 枚举），把安全边界变成模型可预测的操作语言。

### 4.2 对本项目的可借鉴点

| deepcode-cli 手法 | 我们的对应机会 |
| --- | --- |
| 能力注册表 + 条件渲染 | 为 TRIZ 建能力档案（256K 上下文 / thinking 默认关 / qwen3_coder 工具解析 / NVFP4 量化特点），提示词与工具描述按此渲染 |
| 缓存感知布局 | 报告模板、领域知识、写作规范固定前置，吃 vLLM prefix caching（已开启） |
| Skills 按需加载 | TRIZ 的 40 发明原理、矛盾矩阵、ARIZ 做成 skill catalog，不塞系统提示 |
| 容错工具契约 | 报告章节「先读后改」、数据引用护栏、格式自修复 |
| 实证驱动提示词 | 「报告规划模式」提示词 + A/B 量化验证（推理深度、通过率、成本） |
| 专用 compact prompt | 长会话 compact 时保留：用户核心诉求、已定章节结论、术语表、数据台账、待办章节 |

## 5. 综合判断：「5 万字就停」的根因分析

上次任务现象：Agent 写了约 5 万字，自称「受单次输出上限限制，实际无法达到 10 万字目标」。

逐层排查后的根因假设（按可能性排序）：

1. **【最可能】模型把整份报告当成「一次响应」来规划**：没有提示词告诉它「分章写入多个文件、单章控制在 N 字以内」，模型按固有认知认为自己只能在单次输出内完成，于是主动缩减规模到自认安全的长度（约 5 万字 ≈ 81920 token 的中文容量），并把「单次输出上限」当作放弃的理由。**这是提示词/行为问题，不是能力问题。**
2. **【可能】单次 write_file 撞 cap**：即使模型尝试了分章，若某次 `write_file` 的参数内容过长（单章几万字），该次响应会在 81920 token 处被服务端截断，产生不完整的文件，模型可能因此放弃。
3. **【待排除】Octop agent config 配了更低的 max_tokens**：需查 `~/.octop/octop.db` 的 providers/agents 表确认（下一轮动作）。
4. **【已排除】上下文窗口不够**：256K 窗口，5 万字报告 + 提示远未占满。
5. **【已排除】Harness 硬编码上限**：Harness 主链不传 max_tokens，无硬编码上限。

### 解决方向预告（第①步方案候选，待讨论定稿）

- **A. 提示词/编排层（优先）**：任务提示词明确要求「大纲→分章→每章独立 write_file→单章 ≤5000 字→最后合并」；或利用 plan 模式 + subagents 并行写章节。
- **B. Harness 层**：为长文任务加「报告生成」机制（章节状态机、写章工具、自动合并、断点续写）——等 A 的基线暴露问题后再定。
- **C. 服务端**：81920 cap 可调大（vLLM 启动参数），但不解决根本问题，仅作后备。
- **D. 配置层**：确认/调整 Octop agent config 的 max_tokens 与 max_input_length。

## 8. 根因确认（2026-10-16 补充，第 2 轮排查）

**已确认的根因**：用户提供的原始任务提示词中，「核心指令（最高优先级）」明确要求——

> 本次任务的核心诉求是压测你的单次输出上限。你必须在一次回复中一次性完成全文输出，严禁分批执行……

模型忠实执行了该指令：在一次响应内持续输出，接近服务端 `max_new_tokens=81920` 的容量（中文约 5 万字）后收尾，并如实报告「受单次输出上限限制」。**这不是能力问题，是提示词亲手制造的行为问题。**

### octop.db 排查结果（排除假设 3）

- Provider `Meerkat`：`base_url=http://192.168.60.102:8000/v1`，启用模型 `Meerkat-TRIZ-v1`，元数据 `context_window=256000, max_tokens=64000`；
- 该 `max_tokens=64000` 经 `store.py → ModelConfig.from_dict` 进入 harness，但仅作元数据（上下文预算），**不绑定到请求**（harness `llm/factory.py` 主链不传 max_tokens）；
- 当前唯一 agent `main`（general-assistant 模板）的 `config_json` **未设置 max_tokens**；
- 激活模型 = `Meerkat/Meerkat-TRIZ-v1`。
