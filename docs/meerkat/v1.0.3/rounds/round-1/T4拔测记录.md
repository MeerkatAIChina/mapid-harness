# T4 断流自动续跑：模拟拔测记录

> 日期：2026-10-20 · 对应执行计划 T4 验收口径：「模拟断流 → turn 内自动恢复 → 写进 rounds/round-1/」
> 结论：**拔测通过**。耐心重试三层链路（SDK 内部重试 → 内层 patient_retry → 外层 Octop retry）全部按设计工作。

## 测试一：配置注入故障（改坏 base_url → 127.0.0.1:9）14:18 ~ 14:39

验证了重试分层与耗尽形态，同时暴露了拔测方法的盲区。

- 内层 patient_retry 周期 = 6 次尝试，退避 15s→30s→60s→120s→120s；外层 Octop ModelRetryMiddleware 开启 3 个内层周期（date_injection 日志可判读周期边界），**合计 18 次尝试 = 设计的 (5+1)×3 上限，一次不差**。
- 耗尽后走既有优雅终止：`turn failure kind=model_retry` → 前端 stream_error，无崩溃、无脏状态。
- **盲区发现**：模型 client 在首次调用时构建并缓存配置，turn 内改回正确地址**救不回 in-flight turn**——配置注入法只能验证重试分层，无法验证「turn 内自动恢复」。
- **实测总耐心约 21 分钟**（14:18:35 → 14:39:06），比 T4 决策记录估算的「约 12 分钟封顶」长：openai SDK 每次尝试内部再重试 2 次（0.4~1s 退避）+ 连接超时（每次 ~3~7s）叠加所致。全量轮评估断流等待时长应以实测值为准。

## 测试二：真实服务断流（docker stop vLLM）15:12 ~ 15:19 ✅

忠实模拟「配置正确、服务不可达 → 恢复」的真实断流。

| 时间 | 事件 |
|---|---|
| 15:12:32 | turn 启动（date_injection 注入日志） |
| 15:12:40 → 15:17:13 | patient_retry warning ×5，退避 15s→30s→60s→120s 逐条清晰 |
| ~15:14 | vLLM 重新启动（docker start），约 3 分钟就绪 |
| ~15:19:18 | 内层第 6 次重试命中恢复的服务，流式答复开始 |
| 15:19 | 前端自动收到答复，**全程 0 人工干预**（未点「继续」） |

验收三口径全达成：重试日志可见 ✅ / turn 内自动恢复 ✅ / 0 人工干预 ✅。

## 附带发现（备查）

1. **`docker pause` 不能用于断流模拟**：pause 只冻结进程，容器内核 TCP 栈仍完成握手 → 连接建立但永不返回 → 客户端挂起等读超时（SDK 默认 600s），一次尝试就烧光重试预算。须用 `docker stop`（连接被拒、快速失败）。
2. **Windows 防火墙出站 Block 规则对本机→LAN 的阻断未生效**（规则 Enabled/Outbound/Block/Profile Any 均在，Test-NetConnection 仍通）——原因未查明，弃用该方案，仅作记录。
3. 第一次拔测的「client 缓存配置」行为提示：若未来做 host 层自动重发「继续」（T4 Option 2 候补），重发前无需考虑配置热更新——配置变更必须等 turn 结束才生效。
